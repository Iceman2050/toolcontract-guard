# ToolContract Guard — OVERLAP GATE vs Trace2Contract

**Gate:** Idea 5 (final idea), GODMODE v2.0 Five Business Ideas program — overlap inspection only. Build nothing, upload nothing in this gate.
**Date:** 2026-11-11 · **Inspection basis:** source code read on disk, not README alone.
**Suspect:** `trace2contract` v0.1.0 — local source `~/workspace/github-repos-build/trace2contract/`, live at https://github.com/Iceman2050/trace2contract (shipped 2026-11-11).

## VERDICT: PROCEED — distinct repo

ToolContract Guard is **not** an expansion of, and must **not** be folded into, Trace2Contract.

Trace2Contract demonstrably covers **0 of ToolContract Guard's 8 scope items in substance** (1 item — test generation — exists only in its weakest form, see §2). It is a ~250-line, single-command, HAR-in converter whose input direction is the inverse of ToolContract Guard's: Trace2Contract *creates* a minimal spec from observed traffic; ToolContract Guard *audits an existing, authored spec* — and, with permission, a live staging API — for constraints an AI agent cannot see. Folding ToolContract Guard in would mean adding essentially the entire proposed product (a spec parser it does not have, a constraint analyser it does not have, a test executor it does not have, a SARIF reporter it does not have) into a converter whose sole command takes a HAR file, not a spec. That is a new product wearing an old repo's name, not an expansion.

The defensible differentiation is exactly the three-part wedge named in the program brief, and all three parts are verified absent from the suspect's source:

1. **Constraint-gap linting** — finding constraints stated in prose `description` fields but missing as machine-checkable schema keywords (`minimum` / `maximum` / `minLength` / `maxLength` / `pattern` / `format` / `enum` / `required`). The SilentProbe gap. Trace2Contract never reads a `description` for analysis and never emits or checks any of those keywords (§1, §3).
2. **Staging behaviour verification** — executing generated tests against an *authorized* staging target and detecting documented-vs-observed discrepancies. Trace2Contract executes nothing; it writes a test file for someone else to run, and it has only one source of truth (the capture), so there is nothing to discrepancy-check against.
3. **SARIF / CI enforcement** — lint findings as a report + CI result, including SARIF output for code-scanning. Trace2Contract emits two files (a spec, a test file), has no findings, no severities, no exit-code gate, and no SARIF anywhere in the tree.

**Hard rule carried from the brief, binding on the build:** do NOT reproduce the SilentProbe research repo. ToolContract Guard is a maintainable developer workflow — lint + permitted staging tests + actionable fixes + CI enforcement — not a research replication. The SilentProbe figures (~15.2% of parameters declaring any machine-checkable constraint, ~40.1% describing constraints in prose only) are motivation/citation for why the gap matters, not a dataset or result to recreate.

## 1. What Trace2Contract actually is (from source)

A single-purpose converter: **HAR file → OpenAPI 3.0.3 spec → generated contract-test file**, with secret redaction on by default. The whole product is two Python modules.

- **CLI — one command only** (`trace2contract/cli.py`, 13 lines): one subparser, `convert`, with a required positional HAR path plus `--openapi`, `--tests`, `--no-redact`. There is no `inspect`, `lint`, `test`, or `report` subcommand, no `--spec`, no `--target`, no `--format`. Success prints one line — `paths: N (redaction: on|off)` — and returns 0.
- **Core functions** (`trace2contract/core.py`, complete file read): `redact` / `_redact_string` / `_redact_value` (secret redaction), `load_har`, `_template_path` (numeric / long-hex path segments → `{id}`), `_schema_for` (JSON value → JSON Schema), `har_to_openapi`, `generate_contract_tests`, `convert`. No other modules exist (`trace2contract/` contains only `__init__.py`, `__main__.py`, `cli.py`, `core.py`).
- **Input is HAR only — no spec-first input.** `load_har` reads `data["log"]["entries"]`. `convert(har_path, …)` is the only entry point. The OpenAPI spec is an *output artifact*, never an input: no code path opens an existing `.json` / `.yaml` spec for analysis. The one internal spec consumer, `generate_contract_tests(spec)`, receives the dict `har_to_openapi` just built in the same call — it is not reachable from the CLI with a user-supplied spec.
- **Schema inference is type-only** (`_schema_for`): `boolean` / `integer` / `number` / `string` / `array{items}` / `object{properties}`. It never emits `required`, `enum`, `minimum`, `maximum`, `minLength`, `maxLength`, `pattern`, or `format` — for an object it emits `properties` and no `required` list at all. A case-sensitive search of `trace2contract/` + `tests/` for `minimum|maximum|minLength|maxLength|pattern|enum|required` (as schema keywords) and `sarif` returns **no hits in the product code** (the only `required` hit is argparse's `add_subparsers(..., required=True)` in `cli.py`).
- **Requests are barely modelled.** `har_to_openapi` records, per unique path+method: the templated path, the method, the observed response status, and a response-body schema inferred from the single captured body. It does **not** capture query parameters, request headers, request bodies, or parameter objects of any kind — so there are no parameters in its output for a constraint check to even apply to.
- **Its "contract tests" assert status codes only** (`generate_contract_tests`): one generated pytest function per path+method that requests `BASE + path` (with `{id}` replaced by the literal `1`, no request body, no parameters) and asserts `status in {<observed statuses>}`. Its own README states the limit honestly: *"Generated contract tests check status codes against the spec; they are a starting point, not a complete test suite."* And the spec limitation likewise: *"Schema inference is from single observed bodies; optional fields and unions are not inferred."*
- **It executes nothing.** Neither `cli.py` nor `core.py` contains an HTTP client call; `urllib.request` appears only inside the *string* of the generated test file. There is no `--target` / staging execution, no `API_BASE_URL` handling in the product itself (that env var is read by the generated file, when a user later runs it elsewhere).
- **No analysis, no report, no CI product.** No `description` field is ever read for analysis (the only `description` in `core.py` is the hardcoded string `"response captured in HAR"` written into outputs). Outputs are exactly two files: `openapi.json` and `test_contract.py`. No findings list, no severities, no lint rules, no SARIF, no report format. `.github/workflows/ci.yml` is the repo's *own* CI (pytest on Python 3.11 + 3.12, plus a `--help` fixture run) — it is not a CI-enforcement product offered to users, and it produces/uploads no SARIF.
- **Test suite** (`tests/test_core.py`, 4 tests; `BUILD-REPORT.md` confirms "Suite: 4 passed"): planted-secret-never-survives (the hard redaction gate), path templating + status presence, contract-test generation presence (`"def test_contract_" in tests`), redaction marker present. No constraint, lint, execution, discrepancy, or report test exists. Fixture: `tests/fixtures/sample.har` (one `GET /widgets/42` → 200).

## 3. The differentiation (the wedge the new repo owns)

ToolContract Guard owns, exclusively in this fleet:

- **W1 — Constraint-gap linting (spec-first, static).** Input is an authored spec with no traffic capture required — the exact population SilentProbe measured (real, published specs, most parameters unconstrained or prose-only). Checks: parameter/property declares no machine-checkable constraint at all; a constraint is recoverable from its prose `description` (e.g. ranges, lengths, formats, allowed values stated in words) but absent from the schema — reported with the actionable fix; inconsistent `required` / `enum` usage; incomplete response schemas. Trace2Contract cannot see any of this: it never receives an authored spec and its own generated specs contain no parameters or constraints.
- **W2 — Staging behaviour verification (permitted, dynamic).** Generated boundary tests are *executed by the tool itself* against a user-authorized staging target, and the observed behaviour is compared with the documented contract — including the silent-failure class: HTTP 200 returned where the contract (or its prose constraints) says the input should have been rejected, or a 200 payload that does not match the documented response schema. Trace2Contract generates a file and stops; it verifies nothing.
- **W3 — SARIF / CI enforcement.** Findings leave as a human report **and** SARIF (GitHub code-scanning compatible) with a CI-meaningful exit code, so a constraint gap fails a pipeline like any other lint error. Trace2Contract has no findings to export and no SARIF surface at all.

Adjacency, honestly stated (reuse, not overlap): a user *could* pipe a Trace2Contract-generated spec into ToolContract Guard as a lint input, and ToolContract Guard findings could inform edits to specs Trace2Contract produced. That is pipeline composability between two distinct tools — capture-derived spec creation feeding authored-spec auditing — and it strengthens, rather than weakens, the case for two repos with a clean boundary (see §5).

## 5. Boundary note the new README must carry

The `toolcontract-guard` README must include, verbatim in substance, a boundary section stating:

> **How this differs from Trace2Contract.** Trace2Contract (https://github.com/Iceman2050/trace2contract) goes from *observed traffic to a spec*: give it a HAR capture and it creates a minimal OpenAPI spec and status-code contract tests, with secret redaction on by default. ToolContract Guard goes from *an authored spec (and, with your permission, your staging API) to a verdict*: give it an OpenAPI / JSON Schema spec and it lints for machine-checkable constraints an AI agent cannot see — in particular constraints stated in prose descriptions but missing from the schema — checks required/enum consistency and response-schema completeness, generates and (only against a staging target you authorize) executes boundary tests, reports documented-vs-observed discrepancies including HTTP-200 silent failures, and emits a report plus SARIF for CI enforcement. ToolContract Guard takes no HAR input, infers no specs from traffic, and performs no secret redaction of captures — that is Trace2Contract's job; a spec Trace2Contract generates can be fed to ToolContract Guard as an ordinary lint input. ToolContract Guard is also not sop-contract, which tests agent behaviour against human-approved procedure contracts, not API specs. Finally: ToolContract Guard is a developer workflow tool (lint + permitted staging tests + actionable fixes + CI enforcement); it does not reproduce the SilentProbe research study or its dataset — the study's published finding, that most API parameters declare no machine-checkable constraint and many state constraints in prose only, is the problem this tool exists to catch in your spec. Tests run only against a staging target you explicitly authorize; the tool never tests an API you have not pointed it at.

## 6. Gate conditions carried into any future build

1. **CLI boundary stays as proposed** — `toolcontract inspect|lint <spec>` · `toolcontract test --spec <spec> --target <staging>` · `toolcontract report --format sarif`. Spec-first always: every command must work from a spec alone, with no HAR and no live target, except `test`, which additionally requires the explicit `--target` authorization.
2. **Staging-only execution:** `test` refuses (fail-closed) any target not explicitly supplied by the user in that invocation; no default target, no production probing, no execution as a side effect of `lint` / `inspect` / `report`.
3. **Actionable fixes, not just counts:** every lint finding names the parameter/property, the missing keyword, the prose evidence when a prose-implied constraint was detected, and the concrete schema edit that resolves it — otherwise the tool drifts toward the research-report shape the brief forbids.
4. **Do not absorb Trace2Contract's job:** no HAR parsing, no spec inference from traffic, no capture redaction in this repo. If spec generation from captures is ever needed, it is consumed from Trace2Contract as a separate tool in a pipeline, not reimplemented.
5. This gate inspected source on 2026-11-11 (Trace2Contract v0.1.0, as shipped that day). If Trace2Contract later ships genuine spec-first constraint linting, staging execution, or SARIF output, this gate must be re-run before ToolContract Guard's scope is extended toward those areas.
